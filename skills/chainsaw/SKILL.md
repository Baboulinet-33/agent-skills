# Chainsaw

Use this skill for Kyverno Chainsaw tests.

## Rules

* Do not invent Chainsaw syntax.
* Use syntax supported by the installed Chainsaw version.
* Use existing working tests as examples.
* Use the installed Chainsaw binary as the main source of truth.
* Run `chainsaw lint` after each test change.
* Run `chainsaw test` when a Kubernetes test environment is available.
* Fix errors before you finish.
* Do not change the expected behavior only to make a test pass.

## Official sources

Use only these repositories as external sources.

Chainsaw:

https://github.com/kyverno/chainsaw

Chainsaw examples:

https://github.com/kyverno/chainsaw/tree/main/testdata/e2e/examples

Kyverno:

https://github.com/kyverno/kyverno

Kyverno Chainsaw tests:

https://github.com/kyverno/kyverno/tree/main/test/conformance/chainsaw

Do not use forks, mirrors, or third-party repositories unless the user
explicitly asks for them.

## Source priority

Use sources in this order:

1. Installed Chainsaw binary.
2. Schemas generated from the installed binary.
3. Existing tests in the current repository.
4. Official Chainsaw examples.
5. Official Kyverno Chainsaw tests.
6. Other official documentation.

Do not use an arbitrary web example when an official example exists.

## Check the version

Before you create a test, run:

```bash
chainsaw version
```

Chainsaw syntax can change between versions.

Use examples that match the installed version when possible.

Do not assume that an example from `main` works with an older Chainsaw
version.

## Generate schemas

Do not copy Chainsaw schemas into this skill.

When schemas are useful, run:

```bash
chainsaw export schemas <directory>
```

Use schemas generated by the installed Chainsaw binary.

Do not download a schema from another source when the installed binary
can generate it.

## Before creating a test

Do these steps:

1. Check the Chainsaw version.
2. Inspect existing Chainsaw tests in the current repository.
3. Identify the behavior that the test must verify.
4. Find a similar official example.
5. Generate schemas if needed.
6. Reuse the existing test pattern.
7. Create the smallest test that verifies the behavior.

## Generic Chainsaw tests

For generic Chainsaw behavior, use:

https://github.com/kyverno/chainsaw/tree/main/testdata/e2e/examples

Use these examples for:

* test structure;
* steps;
* resources;
* assertions;
* bindings;
* commands;
* waits;
* cleanup;
* other Chainsaw features.

Do not copy an example without checking its compatibility with the
installed Chainsaw version.

## Kyverno tests

For Kyverno policy tests, use:

https://github.com/kyverno/kyverno/tree/main/test/conformance/chainsaw

First identify the Kyverno behavior.

Examples include:

* validate;
* mutate;
* generate;
* cleanup;
* policy exceptions;
* background processing;
* reporting.

Find a test with similar behavior.

Reuse its structure.

Adapt the test to the requested policy and resources.

Do not create a new pattern when an existing Kyverno test already shows
the required pattern.

## Create the YAML

Follow these rules:

* Use valid Chainsaw resources.
* Use the installed Chainsaw version.
* Use existing examples.
* Keep the YAML small.
* Add only required resources.
* Add only required steps.
* Add only required assertions.
* Add only required waits.
* Do not add features that are not needed.

## Validate the YAML

After creating or changing a test, run:

```bash
chainsaw lint <path>
```

If lint fails:

1. Read the complete error.
2. Identify the invalid syntax or structure.
3. Fix the test.
4. Run `chainsaw lint` again.

Repeat until lint succeeds.

## Run the test

When a Kubernetes environment is available, run:

```bash
chainsaw test <path>
```

If the test fails:

1. Read the complete error.
2. Identify the failure type.
3. Check the relevant official examples.
4. Fix the smallest possible problem.
5. Run the test again.

Do not hide a failure.

Do not change the expected result only to make the test pass.

## Failure types

Classify failures before fixing them.

Possible causes include:

* YAML syntax;
* Chainsaw schema;
* Chainsaw syntax;
* Kubernetes resource;
* Kubernetes timing;
* assertion;
* binding;
* Kyverno policy;
* test environment.

Fix the real cause.

## Completion

A test is complete when:

* the YAML uses the installed Chainsaw syntax;
* `chainsaw lint` succeeds;
* `chainsaw test` succeeds when execution is possible;
* the test verifies the requested behavior.

If a Kubernetes environment is not available, say that the test was
linted but not executed.

Do not say that a test is verified if `chainsaw test` did not succeed.
